4. QMD Syntax/Layout Consistency

All of the following are cosmetic — none change parsed structure, heading levels, or fenced-div nesting depth. Verified render-safety by checking Pandoc’s fenced-div and attribute-parsing rules before including anything here.

Safe to batch

  1. Fenced-div class syntax: bare word vs. braced dot-class. normative-conformity.qmd uses bare ::: columns / :::: columns (lines 63, 89, 110) where every other file uses ::: {.columns} / :::: {.columns} (6 instances across _05-example-table.qmd and dataviz-best-practices.qmd:81). Pandoc treats ::: className and ::: {.className} identically — purely a style choice. Recommend standardizing on the braced form since it’s already the 2:1 majority convention.

  2. Space between fence marker and opening brace. 14 instances of :::{ (no space) vs. 303 instances of ::: { / :::: { (with space):

    • _04-example-line-chart.qmd:3,79,124,217
    • _06-example-text.qmd:13,22,34 Pandoc doesn’t require the space; recommend adding it to match the dominant style.

  3. fragment-index attribute quoting. Quoted (fragment-index="1") in _04-example-line-chart.qmd (8 instances) vs. unquoted (fragment-index=1) in _02-cognitive-load.qmd (16 instances) and _03-data-pixel-ratio.qmd (6 instances). Both parse identically as a Quarto/reveal attribute; recommend picking one (unquoted is the majority, 22 vs 8).

  4. Double space after heading marker. _01-intro.qmd:15 — ## {.center ...} (two spaces) vs. every other bare-attribute heading in the project using a single space. One-line fix.

  5. Class/attribute ordering within fenced-div and span attribute lists. .fragment appears in every possible position — first (_01-intro.qmd:22 {.fragment .slide-body-heading}), last (_01-intro.qmd:54 {.slide-body-heading .fragment}, normative-conformity.qmd:64 {.column width="50%" .center-col .norm-speech .fragment}), and middle (_02-cognitive-load.qmd:14 {.absolute .memory-detail .memory-detail-1-5 .fragment .fade-in-then-out ...}). This is scattered across roughly 30 attribute blocks in _01-intro.qmd, _02-cognitive-load.qmd, _03-data-pixel-ratio.qmd, _04-example-line-chart.qmd, and normative-conformity.qmd. Attribute order inside {...} has no effect on Pandoc/reveal.js rendering, so this is safe to normalize — recommend a fixed convention, e.g., positioning/structural classes → .fragment/animation classes → fragment-index → geometry attrs (top/left/width) → style last, and I’d want you to confirm the convention before I touch ~30 lines rather than guessing at your preference.

Uncertain — needs discussion (not proposed as safe fixes)

  • Nested fenced-div colon counts. index.qmd:81–94 opens with :::: {.columns} (4 colons) but a directly-nested ::: {.column width="62%"} (3 colons) itself contains two more 3-colon divs (.title-text, .subtitle-text) at the same colon count as their parent. Pandoc’s fence-matching algorithm can be sensitive to this (“outer fence needs ≥ colons of anything it contains” is the safe convention; matching counts on parent/child is technically allowed but is exactly the kind of thing that renders correctly today and breaks on a Pandoc version bump or minor edit). This currently renders fine, but I’m not proposing to “fix” the colon counts since a wrong edit here is a real rendering-breakage risk — this needs your explicit review, not a batch pass.

  • <br> vs. other line-break mechanisms. Raw HTML <br> is used ~13 times across 5 files for forced line breaks in short text. Separately, _02-cognitive-load.qmd:64–67 uses a trailing backslash (\) at end-of-line inside .digit-wall to force line breaks within one dense block of digits. These aren’t really serving the same purpose (short thematic breaks vs. exact wrapping inside a single content block), so “unifying” them isn’t obviously correct — surfacing this so you can decide if it’s worth touching, not proposing a change.
